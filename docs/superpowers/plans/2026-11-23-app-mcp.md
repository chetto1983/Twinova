# Plan: the open app driven over MCP, with screenshots, and a release one can use (ROADMAP 2.8)

## Goal

An agent drives the Twinova window a person has open, sees it through screenshots, and reaches every feature of the app
over MCP; the release installs the agent beside the app, with example lines and a guide.

## Architecture

- **`twinova-mcp`** (new crate, rmcp 3.9.0): the tools' schemas and router, written once over a `Host` trait.
- **Headless host:** today's agent session (`agent/src/session.rs`) behind the trait. `twinova-agent` serves it.
- **App host** (`src/mcp_host*.rs`): the app's state behind the trait; each tool calls the function its Tauri command
  calls, then emits `snapshot`, `project-changed`, `sources-changed` or `hold-changed`; the webview listens.
- **Window tools** (app host): `screenshot` through WebKit's snapshot (Linux) and WebView2's `CapturePreview`
  (Windows); `show` as an event the webview applies.
- **Distribution:** `twinova-agent` as the bundle's `externalBin` and as release files; `--app` bridges stdio to the app.

## Tech Stack

Rust (rmcp 3.9.0, axum 0.8.9, tokio), Tauri 2.12.5 (`with_webview`), webkit2gtk 2.0.2 with cairo-rs 0.18.5 (`png`),
webview2-com 0.39.1, Svelte 5.

## Spec

`docs/superpowers/specs/2026-11-23-app-mcp-design.md`, from the user's direction of 2026-11-23 ("L'MCP deve pilotare
l'app aperta, vai con tutto e fare gli screenshot").

## Global Constraints

- One tool set: a tool is never written twice, once per host.
- Every tool has an end-to-end test through a real MCP client; the app host's through the running app, checked in the
  window.
- Files under 600 lines; coverage at least 85 %; mutation with no survivor on the new crate.
- Loopback only; the server can be turned off.

## Review Focus

- The window follows every tool that changes something (decision 3): no tool leaves it stale.
- A tab with edits of its own is never overwritten by an agent's write without its notice.
- The screenshot is the window as drawn, on both platforms.

## Decisions taken while writing this plan

1. The trait's methods are the tools' bodies; the tools' argument and answer types live in `twinova-mcp`, so both hosts
   and the tests share them.
2. The app host runs the HTTP server on Tauri's tokio runtime, started in `setup`, stopped when the app exits.

## File structure

| File | Change |
|---|---|
| `src-tauri/mcp/` (new crate: `lib.rs`, `host.rs`, `tools_*.rs`, tests) | the tool set over `Host` |
| `src-tauri/agent/` | the headless host; `--app` bridge |
| `src-tauri/src/mcp_host*.rs`, `screenshot.rs`, `examples.rs`, `lib.rs` | the app host, the window tools, the examples |
| `src/App.svelte`, `src/lib/*` | events from the agent; `show`; "Open example"; the server's address |
| `e2e/mcp.mjs` | the app driven over MCP, checked in the window |
| `.github/workflows/release.yml`, `tauri.conf.json` | the agent in the release |
| `docs/guide.md`, README, CHANGELOG, ROADMAP | the guide and the documents |
